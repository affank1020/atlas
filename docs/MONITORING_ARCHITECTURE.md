# Monitoring audit and phased architecture

Audit baseline: Atlas `main` (2026-10-21, commit `093d780`). This document records known source limitations, rather than treating a currently missing adapter as healthy.

## Existing sources

| Source | Implementation | Status and intended location |
| --- | --- | --- |
| Core changes / store revisions | PostgreSQL `audit_events`; `get_audit_history`, `get_recent_activity` | Authoritative immutable structured changes; Monitoring Activity |
| Workspace / git / dev requests and outcomes | Same audit table, attempt IDs in `after_state` | Keep request/result grouping; Monitoring Activity |
| Project Overview and Activity | `ProjectOverview.tsx`, `ActivityPreview.tsx`, `ActivityFeed.tsx` | Overview uses an on-demand five-operation safe Monitoring preview with View all; the Project Activity tab now reuses the full Monitoring reader with a fixed Project scope |
| Store audit history | `StoreAudit` in `App.tsx` | Keep revision evidence until scoped replacement has feature parity |
| Node recent activity | `NodeIdentity.activity` queries `after_state.nodeId` | Not a separate audit database; metadata association differs from `workspace_id` |
| macOS Node logs | `node-logs.ts`, approved `node.log` / `node-error.log` | Read-only 256 KiB scan, <=200 lines, <=48 KiB redacted output |
| Linux Node logs | `journalctl` for fixed `atlas-node.service` unit | Read-only adapter with a 200-line / 48 KiB tail, no shell or caller-controlled journal units; returns unavailable without privilege escalation |
| Live Server and Node health | `get_monitoring_health` from PostgreSQL `SELECT 1`, effective Node registry/heartbeat | On-demand read-only Monitoring Overview. Database failure, revoked/offline/unavailable/stale/unknown Nodes are distinguished; no fake CPU/disk/memory claims |
| Atlas Server diagnostics | in-memory fixed-code ring, current server process | Bounded, non-sensitive operational diagnostics in Monitoring Logs; separate from Docker stdout/stderr |
| Retained Server diagnostic signals | PostgreSQL `atlas_server_diagnostic_events` | Best-effort 14-day fixed-code history across restarts, capped at 100 per read; incomplete coverage possible, separate from container stdout/stderr |
| Application output | Football Training trainer consoles and per-run output | Remains inside its application; dispatch and infrastructure failures belong in Monitoring |
| Global search | Node log action, activity shortcut and node links | Route operational searches to Monitoring as sections gain parity |

## Known gaps and boundaries

* A 200-row newest-first fetch followed by browser-only filtering misses older matches and creates false empty states. Monitoring now queries the audit table before applying a bounded page.
* Historical audit entries contain a checkout-style `workspace_id`; they are **not** logical Workspace IDs. Monitoring now accepts an explicit `logicalWorkspaceId` filter and resolves it through registered `workspaces.logical_workspace_id` membership **at query time** for both row and grouped-operation modes, including archived checkouts on different Nodes. This is a current-membership view of retained audit history, not a historical reconstruction of former grouping: repository reconciliation can change which logical Workspace a checkout belongs to. Existing `workspaceId`/`checkoutId` filters remain physical and are intersected with logical, Project, and Node filters when combined. Node filtering also resolves a registered checkout's owning `node_id`, since Git inspection and mutation audit JSON may omit it; existing audit-metadata Node attribution remains supported. Demo mode rejects logical scopes explicitly instead of returning unrelated fixture activity. Core/Node events without checkout IDs cannot be attributed to a logical Workspace and are excluded. This read path never rewrites audit rows. JSON snapshot fallback has no authoritative checkout mapping, so an explicit logical filter fails rather than returning misleading results. The Workspaces inspector links to both all logical Workspace activity and its selected checkout's activity.
* Attempt correlation is historically encoded inside `after_state`. Monitoring Activity now opts into group-before-pagination, using the project, checkout and string attempt ID to correlate request/result/failure rows. The current SQL page counts operations, matches filters across their members and returns at most one representative request, success/result and failure row per operation; `get_audit_history` remains the source for complete audit revisions. Older callers of `query_monitoring_activity` retain row-based pagination by default. Time filters apply to the latest member timestamp. This is not distributed tracing and cannot link records without a shared attempt ID.
* Correlated PostgreSQL pagination materializes only compact IDs, timestamps, grouping keys and boolean predicates, then joins full audit snapshots **after** choosing the operation page. A regression test runs `EXPLAIN (ANALYZE, BUFFERS)` over 10,000 synthetic audit rows with large before-state snapshots, once globally and once project-scoped. This guards against wide-row materialization, but it is not a production-scale latency guarantee: exact counts still require scanning/aggregating the eligible history, and deeper growth may call for a bounded or precomputed operation-read model.
* Failures recorded as `workspace.mutation_failed`, unsuccessful development runs, and explicit outcome fields are distinct from pending requests. Unknown/incomplete operations must not be described as successful.
* Audit payload snapshots can contain record data, paths, output or secrets. Monitoring Activity now opts into a **server-side allowlisted detail projection** using `safeDetails: true`; operation correlation and filters run against the authoritative complete audit first, then returned rows omit `previous` and only forward bounded/validated metadata from `resulting` (attempt, operation, Node IDs, task/command identifiers, outcome, duration, exit code and boolean status/truncation flags). Arbitrary errors, paths, stdout/stderr, nested content and record snapshots are never sent by this new UI read. Other legacy audit/history clients and tool modes retain their existing full-snapshot contract, so this is data minimisation for Monitoring, **not** a new authorization boundary or a promise that all Atlas audit APIs are redacted. The HTTP `x-atlas-client` header is treated as request attribution, **not** an implicit Monitoring `client` filter; explicit client filters still apply. When safe history omits arbitrary `workspaceName`/`name` fields, rows fall back to the preserved, stable Workspace ID rather than misleadingly displaying “Unknown workspace”; a separately supplied authorized names map can still show real names. Share activity offers distinct, deduplicated source/target Node links. Project/Workspace/Node/Store activity links use the existing scoped Monitoring route.
* The macOS log adapter redacts known token patterns and refuses paths/symlinks; it does not guarantee full retention or universal redaction. Logs remain bounded tails, never archive evidence.
* Node lifecycle is partly in audit rows (via `NodeIdentity`), but not all runtime events have a complete project / Node association. Do not imply comprehensive event coverage.
* Atlas Server diagnostics capture only fixed operational event codes, never user input or exception text. The in-process ring is erased on restart. A separate PostgreSQL source stores fixed codes, timestamps and random process IDs for a 14-day read window, but asynchronous writes can be lost and previous-process loss cannot be reconstructed. Missing migration or database connectivity returns `available: false`, not an apparently complete empty history. **Neither source reads historical container stdout/stderr**; that still requires a separately reviewed, fixed-source and permission-bounded collector.\n* Linux journal reads target only `atlas-node.service` with a fixed journalctl binary and arguments, a three-second timeout, 256 KiB scan and 48 KiB visible output cap. Journal timestamps are retained as emitted. Permission failures return unavailable, never a privileged retry; no shell, arbitrary paths, or caller-selected journal units. Atlas Server process/container logs still require a separate approved adapter.
* The old feed's 5-second auto-refresh is wasteful. Monitoring Activity now defaults to **manual refresh** and offers an explicit, URL-shareable `live=1` opt-in. Live mode requests a new operation page no sooner than 30 seconds **after** the previous read settles, pausing timer work while the tab is hidden and refreshing on visibility restoration **only when the 30-second cooldown has elapsed** (otherwise scheduling the remaining delay). Fast visibility toggles cannot cause request bursts. Switching filters, browsing a different page or leaving Monitoring aborts the previous scoped read, and stale responses cannot replace a new scope. Toggling live updates on/off only installs or removes the polling timer, preserves settled Activity rows and lets an in-flight read finish without creating another request. The most recent request-settlement cooldown persists across rapid Start/Stop toggles. Only the fixed, existing safe Activity query is polled, never Node logs, diagnostic tails or full audit history. Live mode is available only on the newest operation page; paging into historical offsets automatically turns it off, and a deep link with both `live=1` and a nonzero offset is treated as manual. The `live` query-string state is excluded from the Server/MCP tool input, and this is neither a persistent subscription nor a background alert service.
* The authoritative source for specialised model-training logs stays inside Football Training. Copy only meaningful Atlas infrastructure outcomes, not training line streams.

## Live operational health snapshot

The read-only `get_monitoring_health` endpoint checks PostgreSQL with `SELECT 1` (query timeout: 2 seconds) and reads the effective Node registry. It returns one UTC `checkedAt` value, the current Server process start/uptime, database reachability/probe latency and an explicit `nodes.available` bit. Health queries use a separate PostgreSQL pool capped at two connections with bounded acquisition and query timeouts, and each source has a 2.2-second presentation deadline. Even if the application pool is exhausted, the health endpoint returns a conservative degraded/unknown result rather than waiting for the frontend's general request timeout. Real database work is constrained by acquisition and statement/query timeouts, not merely abandoned after a Promise race. Failed reads do not include error text, Node metadata or credentials. The HTTP tool shares the trusted-origin boundary used by Node tools; the MCP tool uses the normal MCP authentication policy. Unknown probe input fields are rejected.

The health-only directory excludes **only** the pristine migration-seeded `local_key='local'`, `runtime='local'` Node when it has never connected, has no credential, is offline, and owns no Workspaces (including archived bindings). Normal Node listings are unchanged; any enrolled, pending, revoked or assigned legacy identity remains visible and can degrade health. This avoids falsely degrading remote-only deployments that never used the old in-process Node.

Node health is based on **effective status and last-seen heartbeat**, not reported host resource metrics. A connected Node with a last-seen timestamp older than 90 seconds is `stale` (the WebSocket gateway already terminates sessions after 45 seconds of missed pongs); revoked credentials take priority, then disconnected/unavailable states. A connected Node without a valid timestamp is `unknown`, never falsely healthy. `overall` is `degraded` for database failure or an actual Node problem, `unknown` if registry/heartbeat health cannot be verified, otherwise `healthy`. Zero registered Nodes alone is not a service failure. There is no automatic remediation, alert delivery or persistent health history.

This is **an on-demand, point-in-time snapshot**, not a continuously monitored SLA. It does not prove Docker/container health, CPU/disk/memory capacity, background job correctness, Ollama availability, external integration health, cross-replica health or durable log retention. Operators can inspect Activity and Logs separately. Future health providers/alerts require distinct reviewed PRs.

## Delivery sequence

1. **Activity and navigation (first PR):** query `audit_events` with parameterised filters, total and offset/limit; preserve legacy audit tools; add Monitoring tabs, deep links and old Activity bookmark support. Basic macOS Node log reader remains read-only. Indexes cover principal read patterns.
2. **Contextual previews (follow-up PR):** Project Overview now uses a reusable five-operation Activity card with server-side Project scoping, `safeDetails: true`, grouped operation pagination, explicit refresh and a scoped **View all activity** link. It does not auto-poll the legacy 200-row audit feed. Selected Nodes now display the same safe, five-operation preview instead of the old NodeIdentity-derived short list; the node-scoped Monitoring deep link includes checkout-owned audit events from that host. The Workspace inspector offers an on-demand, single preview switchable between all logical Workspace checkouts and one selected physical checkout, with explicit failure/unsupported-scope states and no duplicate simultaneous queries. Store details and the Store audit tab now expose a direct, Project-and-Store-scoped link to Monitoring Activity; the existing Store audit revision evidence stays unchanged. Event search in Monitoring is bounded and uses the safe Activity projection, rather than replacing full Store revisions. The Project Activity tab now reuses the Monitoring Activity reader (server-scoped filters, correlated paging, safe details and manual/opt-in live updates) instead of the old 200-row five-second polling feed. Project scope is locked to the current route, including when URL filter parameters are supplied; all other filters and paging are shareable on the Project Activity URL. An **Open in Monitoring** link carries the current query to central Monitoring.
3. **Technical logs (follow-up PR):** Linux fixed-unit journal adapter reuses the existing Node log capability and Monitoring UI with bounded reads and redaction tests; Server-owned diagnostic signals now have a bounded read tool; historical Atlas Server container stdout/stderr still requires a separately reviewed fixed-source collector and authorization.
4. **Operational quality (follow-up PRs):** correlation-aware paging and Server/Node health snapshots are shipped. The next increment adds opt-in safe Activity details and scoped navigation links. Activity opt-in live polling and logical Workspace filter/navigation across Node-bound and archived checkouts are now included; remaining work includes Node lifecycle/runtime audit attribution, health-provider expansion and observability measures.

## Compatibility and validation

* Existing MCP `get_recent_activity` / `get_audit_history` remain unmodified and backed by the same immutable table. The legacy ActivityFeed module remains for compatibility, but Project Activity no longer calls it.
* Monitoring URLs use hash query strings, e.g. `#/monitoring?tab=activity&projectId=...` and `#/monitoring?tab=logs&nodeId=...`. `#/activity` maps to Monitoring Activity for old bookmarks.
* Queries use parameterised SQL and bounded limits; records outside a selected scope must not appear.
* Tests cover deep links, legacy API continuity, filter-before-pagination and Node log boundary semantics. Review CI and production logs separately before retiring old feeds.


## Node lifecycle and update attribution

Monitoring now preserves a constrained distinction between *entrypoint* and *actor*. A Node-control mutation received through the trusted HTTP/MCP dispatch is recorded as `atlas-http` / `atlas-mcp` with fixed `transport` and `actorKind=transport`. The `x-atlas-client` header and arbitrary tool payload cannot change this identity. Local invocations retain `atlas-server` / `server`. These fields do **not** attest to a human operator; they only identify the call path.

A successful HTTP one-use enrolment ticket is labelled `client=atlas-node-enrolment`, `transport=http`, `actorKind=enrolment-token`. Authenticated HTTP Node update claim and outcome report events use `client=atlas-node-credential`, `transport=http`, `actorKind=node-credential`, separate from the HTTP/MCP requester that prepared the update. This does not constitute host-root approval or verified software installation. The safe projection retains a validated update-intent UUID, fixed status/outcome words and explicit `approved/executable/verified/clearsClaim` booleans while excluding release metadata, arbitrary names, credentials and errors.

Workspace Node placement now persists `project_id` and `workspace_id` on its immutable audit row in the same transaction. Project/checkout scoped Activity can find the placement, and the before/after Node IDs can each be used as Node Activity filters and navigation links. Historical rows are not rewritten; older unscoped placements remain historical and may not appear in a Project-filtered view.

Share approvals already stored source/target Node UUIDs; their audit rows now also carry trusted transport metadata. Node-scoped filtering continues to admit source/target metadata *only* for share approval/revocation events to avoid accidental association by unrelated JSON keys.

No broader Files/backup/automation human attribution is claimed. Those pathways need a separately reviewed audit of their authorization boundaries, atomic writes, actor evidence, and retention before they are classified as complete in #110.

## Files, folders, and operator backup evidence (migration 035)

New Files and Project-folder metadata mutations insert immutable `audit_events` rows **in the same PostgreSQL transaction** as the metadata. The database triggers cover Web, Node-transfer and internal Files writers without assuming that an HTTP header or stored `created_by` string authenticates an operator. Uploaded, archived, restored, and moved Files and created/renamed/archived/restored Project folders use fixed operation codes under the `files` category. No file contents, key, checksum, filename, folder name, path or raw error enters these rows.

For Files with a valid registered Project owner, `project_id` derives from the database; for registered Workspace-owned Files, `workspace_id` and its Project are resolved from the checkout row. Application-owned Files have no inferred Project attribution: the legacy application slug is not sufficient evidence to claim a unique Project. Only new successful metadata mutations are recorded; old rows are not backfilled, and a rolled-back write has no audit event. The `client` value `atlas-files-db` means **database-level observation**, not a verified human or device identity. File/folder IDs and fixed `source=database-trigger` are projected only for this trusted event family.

The manual R2 recovery-seeding CLI now writes one bounded `backup.r2_seed_observed` event per returned report (including dry-runs), with a per-run UUID and strictly bounded counts/status flags. It never records file IDs, object keys, R2 endpoints, credentials or free-text diagnostic data. Audit storage happens **after** R2 operations and cannot commit atomically with an external bucket: audit unavailability is reported separately. `status=partial` means a page of the catalogue was inspected, not a verified complete backup; `createdVerified` means copies were re-read and hashed, not restored. Reports with `status=failed` or `status=empty` are marked failed in Monitoring outcome filters, because both cause a nonzero CLI exit. Exceptions during R2 reads or PUTs are recorded best-effort as a separate fixed `status=aborted`, `outcome=failed` observation with the same run ID allocated *before* seeding; no inferred success counters or raw errors are stored. An aborted PUT may have committed externally before failure. Audit write failure is surfaced separately and cannot erase this uncertainty.

The host-only encrypted PostgreSQL snapshot script produces a private ciphertext and manifest with `verifiedRestore=false`; it does **not** send an authenticated event to Atlas Server, and Monitoring cannot assert that those backups exist or have been restored. There is currently no general Atlas Server cron/automation execution subsystem with a trusted operation lifecycle to audit; Workspace development-task operations already have separate request/result audit evidence. Do not construct synthetic actors or completion events for absent schedulers.

All new evidence requires migration 035 before runtime writes. A migration failure should block deployment rather than produce an unaudited success. Older Nodes and Web clients remain compatible because the trigger lives in PostgreSQL. The added projection is allowlisted and scoped; raw audit endpoints retain their existing authorized contracts.


## Diagnostic archive readiness and security boundary

The Monitoring health endpoint now performs an independently bounded read against the *fixed diagnostic archive table* through its dedicated single-connection pool, in parallel with the existing PostgreSQL liveness and effective Node heartbeat probes. Thus a responsive primary database does **not** imply retained diagnostics are readable. The archive states are `available` (fixed SELECT succeeded), `unavailable` (SELECT failed, including missing migration), `disabled` (explicitly off), and `unknown` (probe deadline/error). In-process dropped write count, waiting queue size and write backoff are separate signals. These signals are not replicated across past processes; a zero count means only that **this** process has not observed a lost write. An available probe is **not** proof that every event was durably written.

A diagnostic failure or loss changes an otherwise healthy overall snapshot to `unknown` (not a fabricated outage), while a genuinely failed primary database or Node remains `degraded`. An explicitly disabled optional archive does not make primary application readiness fail. Historical reads enforce a server-side 14-day past bound **and** reject events more than 30 seconds in the future; this prevents future-skewed rows from being presented as current. The Web Overview explains unavailable/disabled/backoff status and links to fixed-code retained diagnostics. An old Server response without the new field is rendered as `unknown` rather than crashing during a rolling upgrade.

**Container logging decision:** Production Server is deliberately not given the Docker socket, root, arbitrary host volume mounts, journal authority or permission to invoke `docker logs`. Container stdout/stderr may contain secret material and lacks an existing reviewed retention/redaction contract. Adding generic container-log browsing to the Server now would widen the attack surface beyond the fixed-code Monitoring requirement. Until a privileged *separate*, fixed-source, redacting and permission-bounded collector is engineered and independently reviewed, raw container history is **out of scope**. Operators can investigate container logs through their existing trusted host administration path; Atlas cannot claim that this log source is centrally retained.

Live acceptance remains separate: run the [Monitoring deployment runbook](MONITORING_DEPLOYMENT_RUNBOOK.md) for post-migration scope/privacy, old/new Server interoperability, archival disabled/unavailable/recovered transitions, Node disconnections and network failures. An automated CI pass does not establish deployed retention, browser viewport parity, privilege boundaries or restore correctness.
