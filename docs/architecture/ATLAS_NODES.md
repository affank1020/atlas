# Monorepo Node V2 location

Atlas Server lives in `apps/server`, the standalone Node in `apps/node`, and the version 2 wire contract in `packages/protocol`. Server routes capability calls over the authenticated remote gateway and has no local execution implementation. The desktop Node entrypoint is `apps/node/src/platforms/desktop/main.ts`; its core connection/dispatch logic is separate from capability implementations. The existing Mac Node UUID and credential must be retained across upgrades. Being in the same monorepo does not mean Server and Node are deployed together.

# Atlas Nodes V2

Atlas Server owns projects, Workspace metadata, placement, audit, and Node identity. A Node is a platform-neutral runtime that exposes bounded capabilities. Clients use `Client / MCP → Atlas Server → NodeRouter → Atlas Node → Workspace/runtime`. Server never executes remote Workspace operations locally.

## Identity and enrolment

Migration `012_nodes.sql` created the original UUID and assigned existing Workspaces to it. Migration `014_node_identity.sql` retains that UUID and adds platform, version, credential state, a SHA-256 credential digest, and one-use enrolment tickets. Raw credentials are never stored on Server, returned by list/get tools, or included in audit. The Node operator must keep the UUID and credential in a private configuration file (mode 0600), environment secret store, or equivalent platform vault.

For a new Node, use `create_node_enrolment` from Atlas Web or MCP. The returned random token expires after ten minutes and can be used once. On the Node host, POST `{ "token": "…", "name": "…", "platform": "…", "version": "…" }` to `/node/enrol` over the same trusted local/private connection. The response contains `nodeId` and `credential` exactly once. Save these as `ATLAS_NODE_ID` and `ATLAS_NODE_CREDENTIAL` in `.env.node`, along with `ATLAS_SERVER_URL` and `ATLAS_WORKSPACE_ROOTS`. Start with `npm run start:node` (or `npm run dev:node`). Use `wss://` outside loopback; the standalone client refuses plaintext WebSocket to non-loopback hosts.

To migrate the original Node, find its UUID with `list_nodes`, then call `rotate_node_credential` for that UUID. Use its returned enrolment token with `/node/enrol`, save the returned credential under `ATLAS_NODE_CREDENTIAL`, and restart the Node. This preserves the UUID, Workspace IDs, placement, paths, and audit history. `ATLAS_NODE_TOKEN` is deprecated and is not accepted by Node V2.

`rotate_node_credential` invalidates the old credential and closes its connection before issuing a bound one-use enrolment token. `revoke_node` invalidates the credential and all unused tickets and closes the connection. A revoked Node keeps its identity and assigned Workspaces; it cannot reconnect until an explicit rotation and reenrolment. Enrolment tickets and credential digests are random, unique, and database-backed. Atlas Web displays only a short-lived ticket; the long-lived credential goes directly to the enrolling Node.

## Connection and placement

The Node opens an outbound WebSocket to `/node/connect` with its own bearer credential. Protocol version 2 registration includes UUID, name, platform, optional version, and capability claims. Server checks the credential against that UUID before attaching the session or accepting Workspace calls. Invalid or revoked credentials fail closed. One live session per UUID is allowed; a later connection replaces the older one. Requests carry UUID correlation IDs, explicit operations, validated input and Workspace binding. Frames are capped at 2 MiB. Timeouts and disconnects reject pending requests without retrying uncertain mutations.

Workspaces have a persisted `node_id` foreign key. `create_workspace` accepts an optional explicit `nodeId`; omission uses the installation's existing default Node. `assign_workspace_node` changes placement with an expected previous Node ID, so stale reassignment attempts fail. Routing only selects the assigned Node. Offline Nodes return `NODE_OFFLINE`; missing capabilities return `CAPABILITY_UNAVAILABLE`; an online Node that cannot bind the assigned Workspace root returns `WORKSPACE_UNAVAILABLE`. No automatic scheduling or Server fallback exists. Reconnecting under the same UUID restores routing immediately.

Capabilities are current session claims (`workspace.files`, `workspace.git`, `workspace.dev`, `unity`), not permanent guarantees. The registry persists the last advertisement for diagnostics, while `list_nodes` and `get_node` present live claims only for attached sessions. Heartbeats update presence without activity events. Enrolment, connection, disconnection, rotation, revocation and placement changes create bounded audit events without secrets. `get_node` includes recent Node activity and assigned Workspaces. Atlas Web supports enrolment, rename, rotation, revocation and reassignment.

The Node revalidates Workspace ownership, root binding, capability, and operation input. File path, symlink, protected content, Git, named dev task, and Unity restrictions remain on the Node. A configured dev task that fails returns its ordinary structured result, distinct from a transport error. Atlas trusts the Server and owner-configured dev tasks; Nodes are not OS sandboxes. Atlas Server remains loopback-bound in remote mode. Hosted deployment, mobile clients, cloud storage, peer communication, multi-user administration, and scheduling are deferred.

Another platform can implement the version 2 WebSocket protocol, store its UUID/credential in a platform vault, advertise supported capability names, and implement only the corresponding bounded operations. Server routing and placement do not need platform-specific branches.

## Controlled development tasks

`workspace_list_dev_tasks` lists the owner-configured names. `workspace_run_dev_task` accepts only a name; the caller cannot supply an executable, arguments, cwd, or environment. For the Atlas monorepo, `npm run workspace:register-atlas` registers the root Workspace; `test`, `build`, `typecheck`, `server_build`, `node_build`, and `web_build` are configured. The 2026 migration archived the old Atlas Workspace ID `eb31ca96-2e91-4390-91ad-c908940d3059` and created `df1c2c81-1383-4533-92ed-b512dbd5646b` on the same Node. AI Football Workspace ID `961d0046-eb49-446d-835e-00bec3e46059` was unchanged. For other Workspaces, a trusted operator uses `scripts/configure-workspace-dev-tasks.mjs` with a local JSON configuration. Each task has an executable, argument list and bounded timeout; the Node runs it in the assigned root with `shell:false` and capped output. Nonzero exits and timeouts remain structured task results.
